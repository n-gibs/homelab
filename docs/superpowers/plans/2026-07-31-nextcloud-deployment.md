# Nextcloud Deployment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deploy Nextcloud as a document store at `nextcloud.nik-homelab.dev`, backed by a CloudNativePG Postgres cluster, with file data on NFS and Prometheus metrics.

**Architecture:** Official `nextcloud/nextcloud` Helm chart 9.2.5 in `apps/nextcloud/` (ArgoCD sync wave 3). Storage splits three ways: Postgres on `local-path` ×3 (replication is the durability), the PHP app tree on `local-path` (fast, reconstructible), and file data on a static NFS PV (the only irreplaceable tier). The chart's Prometheus integration is replaced with a hand-written ServiceMonitor because the shipped one creates a permanently-down scrape target.

**Tech Stack:** k3s, ArgoCD, Helm, CloudNativePG, sealed-secrets, Envoy Gateway (Gateway API), kube-prometheus-stack, Ansible.

**Spec:** `docs/superpowers/specs/2026-07-31-nextcloud-deployment-design.md`

## Global Constraints

- Chart is `nextcloud` 9.2.5 from `https://nextcloud.github.io/helm/` (appVersion 34.0.2). Do not pin to `latest`.
- **No `# renovate:` comment in `app.yaml`.** `renovate.json`'s first custom manager already matches the bare `chartName`/`chartRepo: https://`/`chartVersion` triple; a comment would make the second manager match the same file too.
- All manifests need `resources.requests` and `resources.limits`. The chart ships `resources: {}`.
- Never use `Ingress`. Routing is Gateway API `HTTPRoute` only, parented to `homelab` in `envoy-gateway-system`.
- NFS server is `192.168.30.194` (worker-01), export root `/mnt/storage`, exported `sync` with `no_root_squash`.
- Cluster subnet is `192.168.30.0/24`. Pod CIDR `10.42.0.0/16`, service CIDR `10.43.0.0/16`.
- Never commit `secrets/.secrets`, `secrets/.secrets.generated`, `.vault_pass`, `pub-cert.pem`, or `config/`.
- Never add `Co-Authored-By` trailers to commits. Commits must not reference Claude or Anthropic.
- No `sleep` commands. Use `kubectl wait`, `--timeout`, or readiness probes.
- ArgoCD auto-syncs from `main`. Merge to main = deploy. Per repo convention, main reflects applied state — push, then verify live before moving to the next task.
- CPU/memory request:limit ratios must stay tight (≤1:5). VPA preserves the ratio, so a wide ratio means a lowered request drags the ceiling down with it.

## Task Ordering and Why

1. **NFS directory** — the static PV cannot mount a path that does not exist. Must precede any deploy.
2. **CLAUDE.md exception** — the convention should exist in the repo before code that relies on it, so a reader hitting `local-path` in `html-pvc.yaml` finds the rule already amended.
3. **Sealed admin secret** — the Deployment references it; without it the pod stays in `CreateContainerConfigError`.
4. **Renovate group** — independent of the deploy, but doing it before the app exists means the first bump PR is already correctly grouped.
5. **Deploy app + database, metrics off** — the largest task. Metrics deliberately excluded so a first-boot failure has fewer candidate causes.
6. **Enable metrics** — additive, independently rejectable.
7. **Homepage widget** — requires an app password that can only be minted after first login.

### Task 1: Create the NFS data directory

The static NFS PV in Task 5 mounts `192.168.30.194:/mnt/storage/nextcloud`. An NFS mount of a
non-existent export subdirectory fails, so the directory must exist first. It is created by Ansible
(matching how `downloads`, `media`, and `photos` are managed) rather than by hand, so a rebuilt node
gets it back.

Ownership stays `nobody:nogroup` here — the role's subdirectory loop hardcodes that, and Task 5's init
container fixes ownership to `33:33` on every pod start. Do not try to parameterize the loop's owner;
that is a bigger change than the problem needs.

**Files:**
- Modify: `ansible/roles/nfs_server/defaults/main.yml`
- Modify: `ansible/site.yml`

**Interfaces:**
- Produces: the directory `/mnt/storage/nextcloud` on worker-01, which Task 5's `data-pv.yaml` mounts.

### Task 2: Document the second `local-path` exception

`html-pvc.yaml` in Task 5 uses `local-path`, which CLAUDE.md currently forbids outside replicated
CloudNativePG clusters. Amend the rule before shipping code that depends on it, so the next reader
finds the convention rather than an apparent violation.

The rule is stated in two places and both need to agree.

**Files:**
- Modify: `CLAUDE.md` (Storage section, and the Rules section)

**Interfaces:**
- Produces: the documented convention that Task 5's `html-pvc.yaml` relies on.

- [ ] **Step 1: Amend the Storage section preamble**

Replace:

```markdown
All persistent storage uses the `nfs` StorageClass. Never use `local-path` in new apps — data won't survive node failure. The one exception is a replicated CloudNativePG cluster, where replication provides that durability; see the Rules section.
```

with:

```markdown
All persistent storage uses the `nfs` StorageClass. Never use `local-path` in new apps — data won't survive node failure. There are two exceptions, both in the Rules section: a replicated CloudNativePG cluster, where replication provides the durability, and a volume whose contents are reconstructible from an image.
```

- [ ] **Step 2: Amend the Rules section entry**

Replace:

```markdown
- Never use `local-path` StorageClass for new PVCs, **except** for replicated databases (CloudNativePG clusters with 2+ instances), where streaming replication — not the volume — provides node-failure durability. NFS is not a supported CNPG configuration. Note `local-path` cannot be expanded in place, so size those volumes correctly up front.
```

with:

```markdown
- Never use `local-path` StorageClass for new PVCs, **except** in two cases. (1) Replicated databases
  (CloudNativePG clusters with 2+ instances), where streaming replication — not the volume — provides
  node-failure durability; NFS is not a supported CNPG configuration. (2) Volumes whose contents are
  **reconstructible from a container image**, where the volume is a performance cache rather than a
  system of record — Nextcloud's PHP app tree is the example (`apps/nextcloud/html-pvc.yaml`): ~15k
  small files that would otherwise sit on a `sync`-exported USB spinning disk, and whose loss costs a
  rebuild rather than data. Both cases pin the pod to one node, so `replicas: 1` and a `Recreate`
  strategy are prerequisites, and the recovery path (delete the PVC, let it rebuild) must be written
  down. Note `local-path` cannot be expanded in place, so size those volumes correctly up front.
```

- [ ] **Step 3: Verify no other copy of the rule drifted**

```bash
grep -n "local-path" CLAUDE.md
```

Expected: only the two amended passages plus the storage-example commentary. Every hit that states the
rule must now mention two exceptions.

- [ ] **Step 4: Commit**

```bash
git add CLAUDE.md
git commit -m "docs: allow local-path for image-reconstructible volumes

Nextcloud's PHP app tree is ~15k small files rsynced out of the container image
on first boot and stat-ed on every request. The nfs StorageClass provisions onto
worker-01's sync-exported USB spinning disk, which is the pathological case for
that workload.

The tree is safe on a node-local disk because it is reconstructible: image
contents plus config.php. The tiers that are not reconstructible — the database
and the data directory — stay durable independently.

States the prerequisites the exception depends on (replicas: 1, Recreate
strategy, written-down recovery path) so it does not get cited for volumes that
are actually systems of record."
```

### Task 3: Seal the admin credential

Nextcloud's Deployment mounts `nextcloud-admin` for `NEXTCLOUD_ADMIN_USER`/`NEXTCLOUD_ADMIN_PASSWORD`.

arbitrary internal shared secrets whose value nobody needs to know.

Only the `nextcloud-admin` row is sealed now. The `nextcloud-homepage-creds` row needs an app password
that can only be minted after first login, so it is added in Task 7.

### Task 4: Give Nextcloud its own Renovate group

Nextcloud refuses to skip major versions; 34→36 in one jump wedges the upgrade and needs manual `occ`
recovery. Today every `app.yaml` bump lands in one weekend `helm charts` PR, where a two-major jump
reads as a single line among six unrelated charts.

This does not prevent a skip — `automerge` is already false everywhere, so a human always reviews. It
makes the skip *visible* at the moment of review.

**Files:**
- Modify: `renovate.json`

**Interfaces:**
- Produces: Renovate PRs titled for `nextcloud` alone, separate from the `helm charts` group.

- [ ] **Step 1: Add the packageRule**

In `renovate.json`, add a rule to `packageRules`. It must come **after** the existing
`matchManagers: ["regex"]` rule — later rules win in Renovate, so this one has to override the shared
group, not be overridden by it.

```json
    {
      "matchManagers": ["regex"],
      "matchFileNames": ["**/app.yaml"],
      "groupName": "helm charts",
      "automerge": false
    },
    {
      "description": "Nextcloud cannot skip major versions - 34 to 36 in one jump wedges the upgrade and needs manual occ recovery. Its own PR so a pending bump is never buried in a batch of unrelated charts.",
      "matchManagers": ["regex"],
      "matchFileNames": ["apps/nextcloud/app.yaml"],
      "groupName": "nextcloud",
      "automerge": false
    }
```

- [ ] **Step 2: Validate the JSON parses**

```bash
python3 -c "import json;d=json.load(open('renovate.json'));print([r.get('groupName') for r in d['packageRules']])"
```

Expected: `[None, 'ansible dependencies', 'helm charts', 'nextcloud']` — order matters; `nextcloud`
must be last. (`None` is the `config:recommended` inherited entry if present; the key point is
`nextcloud` after `helm charts`.)

- [ ] **Step 3: Commit**

```bash
git add renovate.json
git commit -m "chore(renovate): give nextcloud its own PR group

Nextcloud refuses to skip major versions, so a bump that sits unmerged for two
release cycles turns the next merge into a version skip that wedges the upgrade
and needs manual occ recovery.

Placed after the shared helm charts rule because later rules win — grouping the
file on its own only works if it overrides the group, not the reverse. automerge
stays false as everywhere; this makes the jump visible at review time rather
than one line inside a six-chart PR."
```

### Task 5: Deploy Nextcloud and its database

The core task. Seven files, metrics deliberately left off so a first-boot failure has fewer candidate
causes.

**Read this before starting — first boot is the risky moment.** The chart enables `livenessProbe` with
`initialDelaySeconds: 10`, `periodSeconds: 10`, `failureThreshold: 3` and leaves `startupProbe`
**disabled**. That gives a starting pod roughly 40 seconds before liveness begins killing it. First boot
rsyncs ~15k files out of the image and runs the Nextcloud installer against an empty database, which
takes far longer than that — so with chart defaults the pod crashloops mid-install and never completes.
Step 2's `values.yaml` enables `startupProbe` explicitly. Do not omit it.

**Files:**
- Create: `apps/nextcloud/app.yaml`
- Create: `apps/nextcloud/values.yaml`
- Create: `apps/nextcloud/postgres.yaml`
- Create: `apps/nextcloud/data-pv.yaml`
- Create: `apps/nextcloud/html-pvc.yaml`
- Create: `apps/nextcloud/pg-backup.yaml`
- Create: `apps/nextcloud/vpa.yaml`

**Interfaces:**
- Consumes: `/mnt/storage/nextcloud` (Task 1), `Secret/nextcloud-admin` (Task 3).
- Produces: `Deployment/nextcloud` and `Service/nextcloud` (port 8080) in namespace `nextcloud`, which
  Task 6's ServiceMonitor and Task 7's Homepage widget target. Also `Secret/nextcloud-database-app`,
  generated by CNPG, with keys `username`, `password`, `host`, `dbname`.

- [ ] **Step 3: Create the database cluster**

`apps/nextcloud/postgres.yaml`. This is `apps/immich/postgres.yaml` with the vector machinery removed —
a document store needs plain Postgres — and 10Gi instead of 20Gi.

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: nextcloud-database
  namespace: nextcloud
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
spec:
  instances: 3
  imageName: ghcr.io/cloudnative-pg/postgresql:18-standard-trixie

  storage:
    # local-path per the CNPG exception in CLAUDE.md: streaming replication, not
    # the volume, provides node-failure durability. Sized deliberately — a
    # document store's DB is metadata only, and local-path cannot be expanded in
    # place, so growing this later means a rebuild.
    size: 10Gi
    storageClass: local-path

  # local-path PVCs already pin each instance to its node permanently, so
  # "required" adds no constraint local-path has not already imposed.
  affinity:
    podAntiAffinityType: required

  resources:
    requests:
      cpu: 100m
      memory: 256Mi
    limits:
      cpu: "1"
      memory: 1Gi
---
apiVersion: postgresql.cnpg.io/v1
kind: Database
metadata:
  name: nextcloud-database
  namespace: nextcloud
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
spec:
  name: app
  owner: app
  cluster:
```

- [ ] **Step 6: Create the database backup job**

`apps/nextcloud/pg-backup.yaml`. Schedule is `45 3` to stagger off Immich's `30 3` so two `pg_dump`s do

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nextcloud-db-backup
  namespace: nextcloud
spec:
  accessModes:
    - ReadWriteMany
  storageClassName: nfs
  resources:
    requests:
      storage: 5Gi
---
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nextcloud-db-backup
  namespace: nextcloud
spec:
  schedule: "45 3 * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: pg-dump
              image: ghcr.io/cloudnative-pg/postgresql:18-standard-trixie
              env:
                - name: PGHOST
                  value: nextcloud-database-rw
                - name: PGUSER
                  valueFrom:
                    secretKeyRef:
                      name: nextcloud-database-app
                      key: username
                - name: PGPASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: nextcloud-database-app
                      key: password
              command:
                - /bin/bash
                - -c
                - |
                  set -euo pipefail
                  out="/backup/nextcloud-$(date +%Y%m%d-%H%M%S).dump"
                  pg_dump -d app -Fc -f "$out"
                  echo "wrote $out ($(stat -c %s "$out") bytes)"
                  find /backup -name 'nextcloud-*.dump' -mtime +7 -delete
                  echo "retained: $(ls -1 /backup/nextcloud-*.dump | wc -l) dumps"
              volumeMounts:
                - name: backup
                  mountPath: /backup
              resources:
                requests:
                  cpu: 50m
                  memory: 128Mi
                limits:
                  cpu: 500m
                  memory: 512Mi
          volumes:
            - name: backup
              persistentVolumeClaim:
                claimName: nextcloud-db-backup
```

### Task 6: Enable metrics

Additive on a working app. The exporter authenticates with the **same** `nextcloud-admin` secret from
Task 3, so no new secret is needed.

**Why the chart's ServiceMonitor is not used.** Its selector is only `name` + `instance` +
`app.kubernetes.io/monitor: enabled`, and `templates/service.yaml` stamps that monitor label on the
**main** Nextcloud Service unconditionally, not just the metrics one. Both Services also expose a port
literally named `http`. So one ServiceMonitor matches both and scrapes `nextcloud:8080/metrics` — Apache
document root, where nothing is served (the openmetrics endpoint is under `/index.php/apps/serverinfo/`).
That is a permanently-down target, and kube-prometheus-stack's default `general.rules` ships
`TargetDown`, which fires when >10% of a job's targets are down. There is no values knob to remove the
label from the main Service.

**Files:**
- Modify: `apps/nextcloud/values.yaml`
- Create: `apps/nextcloud/servicemonitor.yaml`
- Create: `apps/nextcloud/prometheusrule.yaml`

**Interfaces:**
- Consumes: `Service/nextcloud-metrics` (rendered once `metrics.enabled: true`), `Secret/nextcloud-admin`.
- Produces: the `nextcloud_*` metric series in Prometheus.

```yaml
      - nextcloud
```

## Rollback

Per-task, in reverse dependency order:

- **Task 7:** revert the commit; the widget disappears, the app is unaffected.
- **Task 6:** revert the commit; the exporter and both monitoring objects go away. The app is unaffected.
- **Task 5:** `git revert` and push. ArgoCD prunes the Deployment, Service, CronJobs, and HTTPRoute. The
  PV/PVC carry `Retain`, so **file data survives**, as do the CNPG PVCs. Re-applying the same commit
  reattaches to existing data rather than starting fresh.
- **Task 4, 2:** revert; documentation and CI config only.
- **Task 3:** revert the registry row and delete `apps/nextcloud/admin.yaml`. Also remove the values from
  `secrets/.secrets` if abandoning entirely.
- **Task 1:** the directory is harmless if left. Remove it from `nfs_subdirs` and delete it manually only
  if abandoning; `just provision` does not prune.

## Known Risks

- **First boot is the failure-prone moment.** Everything about probes, permissions, and mounts surfaces
  in the first five minutes. Task 5 Steps 15-16 are the real test.
- **The pod is pinned to worker-01.** If that node is drained or cordoned, Nextcloud is down until it
  returns. Same exposure CNPG already accepts.
- **File data has no off-host backup.** Tracked by the `TODO` in `data-pv.yaml`, surfaced by
  `just todos`, owned by the planned `/mnt/storage` backup project. Until then the desktop sync client
  is the second copy — do not treat this as the only copy of anything that matters.
- **Admin password desync.** `NEXTCLOUD_ADMIN_PASSWORD` applies at install only. Changing the password
  in the UI desyncs the sealed secret and makes the metrics exporter 401, which fires `NextcloudDown` and
  points at the wrong thing. Rotate by resealing.
- **Major-version skips.** Before merging any Nextcloud bump: check the chart's appVersion delta, and
  `kubectl -n nextcloud create job --from=cronjob/nextcloud-db-backup nextcloud-preupgrade-$(date +%s)`.
