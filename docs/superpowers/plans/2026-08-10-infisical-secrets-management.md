# Infisical Secrets Management Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace sealed-secrets as the source of truth for the cluster's 20 registry secrets with a self-hosted Infisical instance running at `system` sync wave 0, keeping exactly one sealed secret for Infisical's own bootstrap.

**Architecture:** Infisical runs in-cluster from the `infisical-standalone` chart, backed by a CloudNativePG cluster that generates its own database credential. The Infisical Kubernetes operator materialises secrets from Infisical into native Kubernetes Secrets with identical names and keys, so no application `values.yaml` changes. The operator reaches Infisical over the cluster-internal Service, so secret delivery depends on nothing outside the cluster.

**Tech Stack:** k3s, ArgoCD (ApplicationSet-per-stack), Helm, CloudNativePG, sealed-secrets, Infisical `infisical-standalone` + `secrets-operator` charts, Gateway API (Envoy Gateway), Prometheus.

**Design spec:** `docs/superpowers/specs/2026-08-10-infisical-secrets-management-design.md`

## Global Constraints

- **Never use `Ingress`.** All routing is Gateway API `HTTPRoute` only.
- **Never run `sleep`.** Use `kubectl wait`, `--timeout`, or readiness probes.
- **Never add `Co-Authored-By` trailers** or reference Claude/Anthropic in commit messages.
- **Apply via ArgoCD, never `kubectl apply`** for managed manifests. Push to `main` is the deploy action.
- **Server-side apply only** for ArgoCD-managed resources.
- Chart versions live in `app.yaml` and are managed by Renovate. Never pin to `latest`.
- Per-app ordering uses the `syncWave` key in `app.yaml` (read by the root ApplicationSet template).
- The ApplicationSet hardcodes `destination.namespace` to the directory basename. A manifest must live in the directory whose basename matches its target namespace, or carry an explicit `metadata.namespace`.
- Cluster subnet is `192.168.30.0/24`. NFS server is `192.168.30.194` at `/mnt/storage`.
- Chart versions to use: `infisical-standalone` `1.8.0`, `secrets-operator` `0.11.7`, both from `https://dl.cloudsmith.io/public/infisical/helm-charts/helm/charts/`. **Do not use the `infisical` chart from that repo** — its newest release is 0.4.2 (2024) and still depends on MongoDB.
- Use `InfisicalStaticSecret` (v1beta1). `InfisicalSecret` (v1alpha1) is deprecated.
- **`system/` changes cannot be verified on a branch** — the system ApplicationSet only generates from `main`. System-stack tasks merge to `main` to test. Plan for that: each such task is independently revertable.

## Task 1: Move CNPG and sealed-secrets into the system stack

The riskiest task in the plan. The generated ArgoCD `Application` moves between two ApplicationSets. The ApplicationSet template sets no `resources-finalizer`, so deleting an Application should orphan its resources rather than cascade-delete them, and the new Application should adopt them. **This is reasoning, not a verified fact.** If it is wrong, the `nextcloud` and `immich` CNPG clusters are destroyed.

**Files:**
- Move: `platform/cloudnative-pg/` → `system/cloudnative-pg/`
- Move: `platform/sealed-secrets/` → `system/sealed-secrets/`
- Modify: `system/cloudnative-pg/app.yaml`, `system/sealed-secrets/app.yaml` (add `syncWave`)
- Modify: `secrets/registry.tsv` (no row changes yet — outfile paths for sealed-secrets are unaffected)

**Interfaces:**
- Produces: CNPG operator and sealed-secrets controller reconciling from the `system` ApplicationSet at wave `-1`. Task 3 depends on CNPG being able to create a `Cluster` in namespace `infisical`. Task 2 depends on the sealed-secrets controller and the existing `pub-cert.pem` still being valid — the move must not redeploy the controller with a new keypair.

## Task 2: Seal Infisical's bootstrap secret

`ENCRYPTION_KEY` and `AUTH_SECRET` are arbitrary internal values that never have to match an external system, so they use the registry's existing `generate:` prefix. `seal.sh` generates via `uuidgen | tr -d '-' | tr '[:upper:]' '[:lower:]'`, producing exactly 32 lowercase hex characters — the same shape as `openssl rand -hex 16`, which is what Infisical expects for `ENCRYPTION_KEY`.

**Files:**
- Modify: `secrets/registry.tsv`
- Modify: `secrets/.secrets` (gitignored — add `INFISICAL_SITE_URL`)
- Create: `system/infisical/infisical-secrets.yaml` (generated, committed)

**Interfaces:**
- Produces: Secret `infisical-secrets` in namespace `infisical` with keys `ENCRYPTION_KEY`, `AUTH_SECRET`, `SITE_URL`. Task 3's `values.yaml` references it by name via the chart's `kubeSecretRef`.

- [ ] **Step 1: Add `INFISICAL_SITE_URL` to the gitignored secrets file**

```bash
echo 'INFISICAL_SITE_URL=https://infisical.nik-homelab.dev' >> secrets/.secrets
```

- [ ] **Step 2: Add the registry row**

Append to `secrets/registry.tsv`:

```
infisical-secrets        infisical      system/infisical/infisical-secrets.yaml          ENCRYPTION_KEY=generate:INFISICAL_ENCRYPTION_KEY,AUTH_SECRET=generate:INFISICAL_AUTH_SECRET,SITE_URL=INFISICAL_SITE_URL
```

- [ ] **Step 3: Seal it**

```bash
just seal infisical-secrets
```

Expected output includes `Generated: INFISICAL_ENCRYPTION_KEY`, `Generated: INFISICAL_AUTH_SECRET`, and `Sealed: system/infisical/infisical-secrets.yaml`.

- [ ] **Step 4: Verify the generated key is 32 hex characters**

```bash
grep '^INFISICAL_ENCRYPTION_KEY=' secrets/.secrets.generated | cut -d= -f2 | \
  grep -Eq '^[0-9a-f]{32}$' && echo "KEY FORMAT OK"
```

Expected: `KEY FORMAT OK`. If it fails, Infisical will refuse to start; do not continue.

- [ ] **Step 5: Store `ENCRYPTION_KEY` in all three places — this gates the rest of the plan**

```bash
grep '^INFISICAL_ENCRYPTION_KEY=' secrets/.secrets.generated
```

1. Create a Vaultwarden entry named `Infisical ENCRYPTION_KEY` holding that value.
2. Open a Bitwarden desktop or phone client, sync it, and confirm the entry is visible **with network disabled** — an unsynced client is not a second copy.
3. Create the off-site encrypted copy:

```bash
grep '^INFISICAL_ENCRYPTION_KEY=' secrets/.secrets.generated | \
  age -p > /tmp/infisical-encryption-key.age
```

Store the age passphrase in Vaultwarden and push `/tmp/infisical-encryption-key.age` to a private off-site repo. Verify it round-trips before deleting the temp file:

```bash
age -d /tmp/infisical-encryption-key.age
```

Expected: the original `INFISICAL_ENCRYPTION_KEY=<32 hex>` line.

Losing this key makes every secret in Infisical and every database backup permanently unrecoverable. Do not continue until all three copies exist and the age file has been decrypted successfully at least once.

- [ ] **Step 6: Commit**

```bash
git add secrets/registry.tsv system/infisical/infisical-secrets.yaml
git commit -m "feat(infisical): seal bootstrap secret with generated encryption and auth keys"
```

Do not push yet — Task 3 pushes the whole deployment together, so an `infisical-secrets` Secret never sits in the cluster without the workload that consumes it.

```yaml
  name: infisical-database
  namespace: infisical
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
spec:
  instances: 3
  imageName: ghcr.io/cloudnative-pg/postgresql:18-standard-trixie

  storage:
    # local-path per the CNPG exception in CLAUDE.md: streaming replication, not
    # the volume, provides node-failure durability, and NFS is not a supported
    # CNPG configuration. This DB holds Infisical's encrypted secrets only —
    # small and slow-growing. local-path cannot be expanded in place.
    size: 5Gi
    storageClass: local-path

  # local-path already pins each instance to its node permanently, so "required"
  # adds no constraint local-path has not already imposed.
  affinity:
    podAntiAffinityType: required

  resources:
    requests:
      cpu: 100m
      memory: 256Mi
    limits:
      cpu: "1"
      memory: 1Gi
---
apiVersion: postgresql.cnpg.io/v1
kind: Database
metadata:
  name: infisical-database
  namespace: infisical
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
spec:
  name: app
  owner: app
  cluster:
    name: infisical-database
```

## Task 7: Back up the database to NFS

**Files:**
- Create: `system/infisical/backup-cronjob.yaml`

**Interfaces:**
- Consumes: CNPG Secret `infisical-database-app` from Task 3.
- Produces: dumps at `/data/backups/infisical/` on the NFS share, consumed by Task 9's restore rehearsal.

- [ ] **Step 1: Create `system/infisical/backup-cronjob.yaml`**

CNPG's native backup (barman) targets S3-compatible object storage; NFS is not a valid destination, and running MinIO to satisfy it would be more machinery than the thing being backed up.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: infisical-db-backup
  namespace: infisical
spec:
  schedule: "0 3 * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: pg-dump
              image: ghcr.io/cloudnative-pg/postgresql:18-standard-trixie
              env:
                - name: PGURI
                  valueFrom:
                    secretKeyRef:
                      name: infisical-database-app
                      key: uri
              command:
                - /bin/bash
                - -c
                - |
                  set -euo pipefail
                  ts="$(date +%Y%m%d-%H%M%S)"
                  out="/backup/infisical-${ts}.dump"
                  pg_dump -Fc "$PGURI" > "$out"
                  # Fail loudly on an empty dump rather than rotating a good
                  # backup out in favour of a broken one.
                  [[ -s "$out" ]] || { echo "empty dump" >&2; rm -f "$out"; exit 1; }
                  ls -1t /backup/infisical-*.dump | tail -n +15 | xargs -r rm -f
                  echo "wrote $out"
              resources:
                requests:
                  cpu: 50m
                  memory: 128Mi
                limits:
                  cpu: 500m
                  memory: 512Mi
              volumeMounts:
                - name: backup
                  mountPath: /backup
          volumes:
            - name: backup
              nfs:
                server: 192.168.30.194
                path: /mnt/storage/backups/infisical
```

- [ ] **Step 2: Create the NFS destination directory on worker-01**

```bash

```


- [ ] **Step 3: Add the alert rule**

```yaml
- alert: InfisicalOperatorReconcileErrors
  expr: |
    increase(controller_runtime_reconcile_errors_total{
      job=~".*secrets-operator.*"
    }[15m]) > 0
  for: 15m
  labels:
    severity: warning
  annotations:

    description: >-
      The Infisical secrets operator has logged reconcile errors for 15
      minutes. Existing Kubernetes Secrets are unaffected and workloads keep

      cluster. Check `kubectl -n infisical-operator logs
      deploy/secrets-operator-controller-manager`.
```

```bash
  --alertmanager.url=http://localhost:9093
```

Expected: the alert appears in the Alertmanager UI and routes nowhere, because `trip-test` matches no receiver.
